## 6. What to build

**Stack.** The product's own (§0). Add only: the SDK, a Buffer polyfill if the bundler lacks one, a fetch interceptor for the relayer mock, and the platform's E2E driver if the repo has none. No WalletConnect, no AppKit, no browser-extension adapters unless §0 says the product delegates signing (Appendix A). Visual design follows the product's design system; the feature lives where the product shows the backing BTC account. A standalone app: clean and neutral, phone-width first, dev server on port 3000 (§4.13).

**Architecture requirements.**

1. **Signer adapters from the product's keys, in one module.** `BtcSigner` per §4.9 from the BIP-86 key of the chosen account; `EvmSigner` per §4.10 from the BIP-44 key, instantiated only for the SDK network's chain. Both are wrapped once, at construction, with the prompt counter that drives "signature N of M" (§4.50). A **conformance test** derives both from the harness seed, reproduces a known vault address, produces signatures that verify (BIP-340 over known tapleaf sighashes with the untweaked key; EIP-191 and EIP-712 recovering to the address), then (live) completes one withdrawal and one renewal on signet (done criterion 3).
2. **Key and account strategy** (done criterion 4): which pair backs a line, how the product rediscovers lines on restore (`getPositionId` per candidate pair, bounded gap scan), how borrowing resumes after a sweep (re-fund the same line) and when a fresh pair is needed (§4.7), and how the user is told that the EVM address of the pair is where USDC lands. Decide before the Open screen exists.
3. **Network is the root of state.** Changing it, or applying an endpoint override, tears down the client, the session, every watcher and every cached read, and is refused while any flow is in flight. Mainnet is enabled only when the flag is on and both mainnet endpoints are set; otherwise it is absent from the UI. Show a persistent network banner on signet.
4. **A deterministic boot and resume sequence** on every load, account change and network change: `restoreSession` → `getPositionId` → `getActiveDeposit` → `getPendingWithdrawal` + `getWithdrawStatus` → `getExtensionStatus` → `getCollateralSyncStatus` → `getBorrowMoreSyncStatus` → `syncCollateral` (non-fatal, skipped while a withdrawal or extension is pending, §4.45) → position reads. Model it as an explicit state machine with unit tests for every combination, distinguish in-flight from stuck (§4.35), and offer Resume only when stuck, through **dedicated gates** (`resumeWithdrawal`, `resumeExtension`) that open regardless of debt or expiry. Keep screens mounted while a reboot runs on top of existing data. Re-run the sequence right after any flow that leaves a watcher running (withdraw, resume, renew, finish, add collateral, add-and-draw), not only when the watcher ends: the relayer knows the in-flight state the moment the request lands, and until the plan is rebuilt the buttons stay open and the in-flight card is missing (a pending renewal left Withdraw enabled for its whole duration in one run). Pair every long-lived watcher (withdrawal, extension, collateral sync, borrow-more sync) with a fallback read of its status endpoint every 15 s or so: the SDK's watchers swallow every transport error, so a revoked session or a terminal status they missed otherwise shows only as a card that never clears (facts §4.57); a `SESSION_UNAUTHENTICATED` from that read is the B3 path.
5. **An error-to-UI contract in one module:** for each of the 29 codes, the user copy, the remedy action, whether to retry automatically (never for flows), and whether the position needs re-reading; plus a normaliser for user rejection (EIP-1193 4001, thrown rejections from external signers, Ledger `0x6985` rejected versus `0x6A80` blind-signing-off, and message-text matching per §4.47). Unit-test that every code has an entry and that unknown codes fall back safely.
6. **Prompt choreography.** Before each multi-signature flow, tell the user how many confirmations are coming and what each signs, from the table in §3.9 (a withdrawal is 3 + N signatures for N vault inputs, a renewal 2 + N); show progress; on rejection, show the state the position is in and the way back. Gate every button on state read first (`inLiquidation`, derived end state, `maxBorrowUsd`, pending withdrawal, pending extension, confirmed vault coins) so SDK throws are a backstop, not the UX. A guard that refuses before the SDK is called (a block reason, the fee check, a pending renewal) must still reach the screen as an error: a click handler that swallows it leaves a button that does nothing, which a driver reads as success.
7. **Screens.** Entry point on the BTC account ("Borrow USDC against this BTC"); Markets (wallet-free, quote and collateral calculator); Open a credit line (market, amount, required collateral net of coins already in the vault per §4.25, deposit address with QR and copy, confirmation progress, the relayer's `failure_reason` on a failed deposit with "create a new deposit" as the remedy); Position (collateral in BTC and sats from the vault with confirmed and unconfirmed split and the contract figure beside it, debt breakdown, LTV with health chip, available to draw with margin, available to withdraw capped at confirmed coins with its `limitedBy` reason, expiry as absolute date plus blocks and time remaining, deadline and overdue state, live activities); Add collateral; Draw (routing between `borrowMore` and `borrowMoreSync`); Repay (partial and full with the overpay note and the two-signature notice); Withdraw (destination validation including the own-vault case, fee tiers with a sats estimate from `estimateFeeSats` and the fallback label, partial or sweep, dust clamp and $5 minimum explained, Resume); Renew (proactive and reactive, miner fee and Bitcoin signature disclosed, "resets the term from today" per §4.42, Finish renewal); Position ended (liquidating, liquidated with type and time, expired), and the empty-but-live state after a sweep, which offers Add collateral as the way to borrow again and explains that a new deposit is refused (§4.7); Settings (endpoints per network); Diagnostics (SDK version, `getNetworkConfig`, paths, derived vault address and vault ID, block height and measured rate, raw position and liquidation JSON, storage state, redacted call trace).
8. **Display rules.** Both BTC and sats everywhere; USD to 2 decimals from 6-decimal strings; markets labelled by terms; expiry as date plus relative; nothing from §4.20 rendered as calibrated; explorer links on every txid and hash; copy that names the risk plainly and then the remedy.
9. **Safety rails.** First line capped at the minimum until minted (§4.8); address prefix check before any funding address is shown; destination entered twice or confirmed; mainnet actions show a real-funds confirmation restating amounts, fee and destination before any signature; no action button enabled while its preconditions are unread.
10. **Observability.** Structured logs with secrets redacted by key name and value shape; a redacted SDK call trace on Diagnostics in development; an operator runbook (`docs/RUNBOOK.md`) covering endpoint rotation, SIWE allowlisting and the stuck states below.

**Stuck states and the way out** (what the runbook and the resume screens must cover):

| What the user sees | Meaning | Way out |
| --- | --- | --- |
| "A withdrawal of N sats was authorized but its Bitcoin transaction was never broadcast" | `getPendingWithdrawal().pending` true and `getWithdrawStatus().btcTxHash` null (or status `failed`): the EVM authorization landed; the user rejected a later prompt, lost connection, or Surge refused the fee. Draws and renewals are blocked. | `resumeWithdrawal` with the original destination (remembered per device) and an acceptable fee: one Bitcoin signature plus one EVM envelope. Or wait for expiry. |
| Withdrawal `broadcasted` / `confirmed` for a long time | Normal: pending until the relayer reconciles 3 confirmations. | Nothing; the watcher stops on `finalized`. |
| Withdrawal `finalized` on the explorer but the relayer still reports pending | The notify step never landed. | `reconcileWithdrawal(positionId, txid)`: one EIP-191 signature. |
| "A renewal was requested but its Bitcoin transaction was never broadcast" | `getExtensionStatus()` status `pending`, `btcTxHash` null. Will not self-heal; blocks draws and withdrawals. | `resumeExtension`: one Bitcoin signature plus one EVM envelope, miner fee. |
| Collateral sync `timeout` | The Bitcoin never arrived in the relayer's window. Nothing lost. | Send the BTC, then start the sync again. |
| Deposit `expired` / `failed` | The relayer stopped watching the address; BTC sent there opens no loan and a top-up revives nothing (§4.24). | Hide the address, show `failure_reason`, offer a fresh deposit (§4.25). |
| `RELAYER_OUT_OF_GAS` | Surge's gas wallet is empty; the signature was not consumed. | Retry later; tell Surge. |
| `IDENTITY_CONFLICT` | The key is bound to another Surge identity. | Another pair, or Surge relinks. |
| `syncCollateral` failing on load with `GATEWAY_ERROR` | Expected inside the post-withdraw window or for inactive positions. | None; treat as a warning. |
